crystal-alpha). "current" is `parity/w6-perf01` (batch PERF01 of wave 6); "origin_main"

SQL statements per save: create is now BEGIN, INSERT, COMMIT (3 on sqlite and on
pg; it was 4 on sqlite because each insert also ran `SELECT LAST_INSERT_ROWID()`).
A save that has nothing to write (a clean `save` on a persisted record) now runs no
statement at all: BEGIN is sent with the first statement and COMMIT is skipped when
none ran. Load and update is SELECT, BEGIN, UPDATE, COMMIT.

## What changed

- Hydration builds a column plan once per result set and reads each row by ordinal;
  `find` reuses one statement per model and primary-key type.
- Dirty tracking is lazy: an original value is captured on the first assignment
  that changes it, and a record that is never touched allocates no tracking hashes.
- The empty clause arrays of a fresh relation are shared and copied on first write.
- Rarely used per-record state (nilable flags, the dependent reflection) no longer
  inflates every instance.
- SQLite inserts are cached statements and take the row id from the insert result;
  canonical SQLite timestamps parse without a general-purpose parser.
- Per-record write logs ("Record created/updated/destroyed", "Columns updated") moved
  from info to debug, so a default logger no longer formats and writes a line per save.

## Known remaining costs

- `create` still allocates 16% more than origin_main (BEGIN/COMMIT control
  statements are the cost of atomic save callbacks).
- `bench/relation_chain.cr` worst ratio is 2.57x against the 1.5x guardrail (it was
  2.98x). The remainder is the copy of the query builder on every chain step, which
  needs a persistent (shared-structure) builder to remove.
- The one-model release build is slower to compile than origin_main (27 s against
  17 s) and its binary is larger (2.5 MB against 1.6 MB); that is the parity
  feature surface, not touched by this batch.
