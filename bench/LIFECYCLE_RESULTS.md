# Lifecycle benchmark results

Generated by `bench/lifecycle_compare.sh` on 2026-10-01 (Apple M1 Max, Crystal 1.21.0,
crystal-alpha). "current" is `parity/wave-5`; "origin_main" is Grant before the
ActiveRecord parity work; "v0.23.4" is the last Granite release (aliased as Grant).
Every Grant build linked the same driver versions.

Rerun with `bench/lifecycle_compare.sh --adapter sqlite origin/main v0.23.4`.

## What the numbers say

- **No leaks.** Heap and RSS are flat across repeated create/find/update/destroy
  cycles for the current build on both adapters (origin_main plateaus after its
  third cycle and then stays flat).
- **Queries are the right ones**, with two exceptions on writes:
  - every `save` is wrapped in `BEGIN`/`COMMIT` (added for atomic save callbacks,
    as ActiveRecord does), so create and update each run two more statements;
  - SQLite inserts follow with `SELECT LAST_INSERT_ROWID()` although the insert
    result already carries the id.
- **Reads regressed.** Against origin_main, `find` allocates 2.6x more and takes
  1.75x longer; a 100-row page allocates 2.8x more and takes 2x longer; loading
  2,000 rows allocates 2.8x more (6x the Granite release) and takes 1.85x longer.
  Writes did not regress in time (create and update are faster than before).
- **Compile cost of a one-model program** roughly doubled in the debug build
  (2.4 s / 0.9 GB for Granite, 3.9 s / 0.95 GB for origin_main, 5.1 s / 1.8 GB now)
  and the release binary grew from 1.3 MB to 2.4 MB. The 10-20 GB figure applies
  only to compiling the ~700-model spec suite as one program.

PostgreSQL timings below were taken while other test suites were using the same
server, so treat them as indicative; allocation and statement counts are exact.
The Granite release did not build against PostgreSQL in that run (since fixed in
the benchmark) and is SQLite-only here.
